# harness-eval

評估 AI 開發系統的 Claude Code skill — 跨 6 個維度、40+ 個指標評分設計品質。

不是「這次有沒有跑通」，而是「這個設計有沒有能力持續跑好？」

適用於：Claude Code harness、Cursor rules、Windsurf、Aider、CLAUDE.md 設定，或任何 AI 輔助開發配置。

## 語言版本

| 檔案 | 語言 |
|------|------|
| `SKILL.md` / `SKILL-en.md` | 英文 |
| `SKILL-zh.md` | 繁體中文 |

## 安裝

```bash
mkdir -p ~/.claude/skills/harness-eval
cp SKILL.md ~/.claude/skills/harness-eval/
```

## 使用方式

```
/harness-eval              # 評估當前專案的 AI 開發系統
/harness-eval <path>       # 評估指定路徑的系統
/harness-eval compare <p1> <p2>  # 比較兩個系統
```

**評估範圍說明**：`/harness-eval` 只評估專案層級的檔案（`./CLAUDE.md`、`./hooks/`、`./rules/`、`./settings.json`）。全域 `~/.claude/` 檔案不在範圍內，除非你正在評估一個安裝到全域的 harness repo。沒有這個限定範圍，評估會抓到整個 Claude Code 環境，而不是目標系統。

## 六個評估維度

### 1. 持久力 — AI 能不能在長 session 中持續有效工作？

> AI 在這個系統下能持續有效工作多久才會開始退化？

| 指標 | 評估什麼 |
|------|---------|
| **Context 預算** | always-loaded 指令佔 model context window 的比例是多少？ |
| **使用率上限** | 系統有沒有機制讓長任務的 active context 保持在品質退化閾值（~40%）以下？ |
| **增長上限** | 隨著工作進行，注入的 context 會不會無限增長，還是有上限機制？ |
| **恢復設計** | Context 重置（compact / 開新 session）後，系統能恢復多少狀態？ |
| **恢復鏈路** | 恢復機制的每一步有沒有明確觸發器，還是靠 AI 記得執行？ |
| **連續性設計** | 跨 session 時，工作能不能透過 handoff 和狀態檔銜接？ |
| **退化曲線** | 品質退化是漸進的（有分級的 lite/full 機制）還是懸崖式的驟降？ |

### 2. Context 空間效率 — Context 裡的東西是現在需要的嗎？

> 在任何時刻，context 裡的東西是不是 AI 當下需要的？而且是 AI 自己不知道的？

| 指標 | 評估什麼 |
|------|---------|
| **冗餘度** | 注入的資訊裡，有多少是 AI 從訓練或前文 context 就已經知道的？ |
| **索引 vs 百科** | 主要指令檔是指向細節的短索引，還是自己講完所有事情的巨型百科？ |
| **信噪比** | always-loaded 內容中，有多少比例在當前任務實際用得到（而不只在罕見複雜場景才有用）？ |
| **及時性** | 資訊是在 AI 需要時才注入，還是不管相不相關都預先塞入？ |
| **新鮮度** | 指令檔是每次 agent 出現新的失敗類別就更新的活文件，還是寫完就放著的靜態文件？ |
| **分層** | 靜態規則、動態狀態、參考文件有沒有分成不同層？ |
| **去重複** | 同一概念有沒有在多處重複**定義**（不只是引用）？ |
| **輸出信號控制** | Hook/CI/工具輸出有沒有針對 AI 消費設計——單行錯誤、寫進檔案而非打到 console、輸出聚合統計而非原始資料？ |

### 3. 系統消耗 — 系統消耗了多少資源？值不值得？

> 這個系統本身消耗多少資源？相對於它帶來的價值，值不值得？

| 指標 | 評估什麼 |
|------|---------|
| **固定成本** | 系統無條件在每次 API 呼叫中增加多少 token？ |
| **變動成本** | 每次人類輸入後，系統附加多少 token？ |
| **儀式步驟** | 要「官方完成」一個任務，需要多少流程步驟（不是寫 code 的步驟）？ |
| **啟動流程** | Session 開始時，AI 需要讀多少檔案才能開始實際工作？ |
| **閒置元件** | 在典型使用情境下，有多少比例的 hooks/元件跑了但沒有產出？ |
| **資源護欄** | 有沒有機制防止 agent 在低價值活動上花費不成比例的時間（測試採樣、迭代限制、timeout）？ |
| **觸發點設置** | 每個提醒/檢查有沒有放在最接近動作發生的觸發點，而不是每次 prompt 都觸發？ |

### 4. 遵守度 — 規則實際上能被執行嗎？

> 系統規則實際上能被遵守嗎？有沒有執行機制？

| 指標 | 評估什麼 |
|------|---------|
| **可執行性** | 關鍵規則是有硬閘門（hook block / lint）執行，還是只是軟建議？ |
| **錯誤修復指引** | Hook block 時，錯誤訊息有沒有包含具體可執行的修復指令？ |
| **階段分離** | 系統有沒有強制在寫 code 之前先有規劃階段（含人類確認點）？ |
| **E2E 驗證閘門** | 系統有沒有要求端到端功能驗證才能標記任務完成——而不是「code 寫完了」就算完成？ |
| **反壓設計** | 系統有沒有同時施加上游反壓（引導 AI 走向正確實作）和下游反壓（阻擋不正確的工作）？ |
| **可觀察性** | 能不能事後驗證規則有沒有被遵守？ |
| **一致性** | 規則之間有沒有矛盾？有矛盾時能不能判斷優先級？ |
| **比例性** | 重要規則有強執行力，不重要的規則有較輕的執行力嗎？ |
| **逃生出口** | 當規則和現實衝突時，有沒有明確的 override 或 PAUSE 機制？ |
| **交叉對應** | 指令檔說的規則和 hooks 實際檢查的是同一件事嗎？（沒有 phantom reference 或 unhandled output。）|

### 5. 穩健度 — 系統壞了是優雅降級還是全面崩潰？

> 系統本身會不會壞？壞了會怎樣？

| 指標 | 評估什麼 |
|------|---------|
| **優雅降級** | 一個元件失敗時，其他元件繼續工作，還是連鎖崩潰？ |
| **錯誤隔離** | 一個 hook 報錯會不會中斷整個 session，還是錯誤被 catch 後 session 繼續？ |
| **狀態一致性** | 有幾個 source of truth，它們能不能 drift 出不同步的狀態？ |
| **空狀態** | 在全新 repo、無 SPEC、無 DECISION 的情況下，系統能不能正常工作？ |
| **中途變更** | 人類中途改了 code、需求或 config，系統有沒有偵測和適應的機制？ |
| **版控即紀錄** | AI 做決策需要的所有知識是否都在版控的檔案裡，而不是在外部工具（Slack、Google Docs）？ |
| **熵防禦** | 有沒有機制防止 AI 複製壞模式，且定期清理 AI 生成的低品質 code？ |
| **依賴存活性** | Hooks 和指令引用的所有檔案、script 和路徑是否還存在？ |
| **狀態格式韌性** | 任務/功能狀態是否用機器可解析格式（JSON/YAML）儲存，能抵抗 AI 意外覆寫？ |

### 6. 協作品質 — 人類和 AI 的互動設計好不好？

> 人類和 AI 之間的互動設計好不好？

| 指標 | 評估什麼 |
|------|---------|
| **對的時間給對的資訊** | 系統有沒有在 AI 真正需要時才注入資訊，使用狀態感知的注入機制？ |
| **噪音程度** | 系統在沒有 actionable 資訊時還是會輸出嗎？ |
| **自主分級** | 有沒有明確的分級，定義什麼由 AI 自動執行、什麼要詢問人類（deny/ask/allow）？ |
| **透明度** | 人類能不能透過 progress tracking 和 event log 看到 AI 在做什麼？ |
| **多 Agent 設計** | 多個 agent 能不能協調，且每個 agent 的工具權限有沒有 scope 到它的角色？ |
| **Agent 可觀測性存取** | AI agent 能不能查詢 log、metrics、runtime 狀態、DOM 來自我診斷——而不是只能等人類介入？ |
| **Agent 可讀性** | Stack 用的技術 AI 熟悉嗎（API 穩定、訓練集覆蓋）？可以按 worktree 隔離啟動嗎？ |
| **失敗分析** | 出問題時，系統引導「缺什麼 context/tool/constraint」，還是只是「再試一次」？ |
| **設定對齊** | 權限設定（deny/ask 清單）和指令檔的禁止行為是否一致？ |

## 運作方式

1. **評估範圍** — 定義評估邊界（只評估專案檔案，不含全域 config）
2. **探索元件** — 讀取範圍內所有 AI 指令檔、hooks、狀態檔、設定
3. **開發流程模擬** — 追蹤完整開發生命週期：session 開始 → 寫 code → 完成任務 → 驗證 → compact
4. **假設壓力測試** — 對每個元件提問：「這個假設在當前 model 下還成立嗎？」
5. **評分** — 6 個維度 × 加權指標 → 字母等級（A–F）→ 加權總分
6. **建議** — 最多 5 條可執行的修復建議，按影響力排序

## 評分權重

| 維度 | 權重 | 理由 |
|------|------|------|
| 穩健度 | ×2 | 系統崩潰，其他都無意義 |
| 持久力 | ×1.5 | 決定每個 session 的最大有效工作量 |
| 遵守度 | ×1.5 | 決定工作品質 |
| Context 空間效率 | ×1 | |
| 系統消耗 | ×1 | |
| 協作品質 | ×1 | |

## 設計原則

- **實作無關** — 評估設計品質，而不是這次有沒有跑通
- **範圍限定** — 只評估目標系統，不包含整個 Claude 環境
- **假設壓力測試** — 挑戰每個元件的假設在當前 model 下是否仍然成立
- **流程模擬** — 在評分前先追蹤完整生命週期的 token 消耗
- **已知限制** — 功能正確性與棕地/遺留 codebase 適用性不在評估範圍內

## 系統類型對照

| 類型 | 範例 | 持久力 | Context 效率 | 系統消耗 | 遵守度 | 穩健度 | 協作 |
|------|------|--------|------------|---------|--------|--------|------|
| 裸機 | 完全無設定 | A | F | A | F | A | F |
| 單檔案 | 一個 CLAUDE.md | B | C | B | D | A | D |
| Rules-based | .cursorrules + rules/ | B | B | B | D | A | C |
| Hooks 加強 | CLAUDE.md + hooks | C | B | C | B | C | B |
| 完整 harness | SPEC + hooks + multi-agent | D | B | D | A | C | A |
| 過度設計 | 什麼都加了 | F | D | F | B | D | B |

最適合的類型取決於專案複雜度：
- 週末個人專案 → 單檔案或 Rules-based
- 團隊專案，1–3 個月 → Hooks 加強
- 複雜多 agent、長期專案 → 完整 harness
- 如果系統消耗分數比遵守度分數差 → 可能過度設計了
